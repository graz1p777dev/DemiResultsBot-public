# Передача: что сделано и что не доделано

Срез от 22.10.2026. Ниже разделены результаты предыдущей live-проверки и ещё не подтверждённые сценарии. Не выдавать этот отчёт за текущую доступность сервисов через несколько дней: сначала перепроверить.

## Реально работало на production при передаче

- Интерфейс Самата сохранён, существующие исправления прав не откатывались. CRM login и backend health возвращали HTTP 200.
- WhatsApp переключён на Green API. Пробельное имя клиента нормализуется: устранён SQL constraint error, блокировавший входящие. Для вложений разрешён только точный наблюдавшийся Green media host, не весь облачный домен.
- Реальное сообщение владельца «ChatGPT» восстановлено по исходному provider ID без дубля в CRM/backend. Для приоритетного восстановления это сообщение было повторно подано через исправленный webhook. Это не новый входящий тест.
- Заблокированная фотография затем пришла автоматически; создано одно сообщение и одно вложение. Очередь Green обработалась до **0** без ClearQueue/DeleteNotification.
- Исправлена отправка на канонический WhatsApp LID через CheckWhatsapp. Несколько реальных согласованных тестовых ответов владельцу получили **read**. Последние статусы автоматически дошли до CRM и backend — без ручной сверки.
- Карточки согласования доставлены в личные Telegram-чаты менеджеров. Правка и approve выполнены через авторизованный API CRM с отдельным QA-автором. QA-вопросы для генерации были синтетическими, не клиентскими.
- День: 10:00–21:00 Asia/Bishkek, согласование обязательно. Ночь: фиксированное сообщение один раз за ночь; входящие сохраняются до утра. Celery beat реально запускал утренний sweep каждые пять минут.
- Защита конкуренции: PostgreSQL advisory lock на lead и условные переходы approve/edit/reject/save. Буферы отмечаются обработанными после сохранения черновика. Ошибки AI сохраняют recovery marker, а не теряют входящее.
- OpenAI реально вернул `429 credit_balance_exhausted`. Текстовый fallback на уже настроенный DeepSeek сработал на живом черновике; модель/провайдер сохраняются в метаданных. Это не пополнение баланса и не fallback голосовых/изображений.
- Исправлен приоритет действующих бизнес-инструкций над устаревшей историей. Live checker исправил старый график на 10:00–21:00. Ошибочный QA-ответ был отправлен только согласившемуся владельцу, затем исправление доставлено и прочитано.
- Анонимный доступ и invalid webhook secret отклоняются. Для девяти проверенных финансовых/HR RPC: anon EXECUTE=0, authenticated=0, service role=9. Две синтетические обучающие записи удалены с защищённой резервной копией; аудит отправок сохранён.

## Незавершённая работа — в порядке продолжения

1. **Живые кнопки Telegram.** Человек должен нажать approve, edit и reject в настоящем Telegram; проверить отправку ровно один раз, текст правки и имя действительного сотрудника в аудите. Доставка карточки и API-approve уже подтверждены, но это не проверка Telegram-кнопки. Native UI automation не смогла выполнить клик; callback не подделывался.
2. **Настоящая ночная смена.** Ночь/полночь/утро проверены детерминированно на PostgreSQL, но реальный переход 21:00 → 10:00 не наблюдался. Проверить один шаблон, сохранность нескольких сообщений и одну утреннюю карточку после перезапуска.
3. **Голосовые и медиа.** Реальная транскрипция входящего голоса, vision и исходящие аудио/файлы полностью не проверены. Исчерпанный OpenAI баланс остаётся внешним ограничением; текстовый fallback это не исправляет. Не терять вложение при ошибке AI.
4. **Полные пользовательские сценарии CRM.** Запись/изменение/отмена консультации, сотрудники, разные роли, права чужого клиента, финансы/HR, CRUD и мобильный интерфейс требуют проверки на отдельной базе и затем ограниченного smoke. Read-only SQL и unit tests не равны реальному входу сотрудника в браузере. Не проводить настоящие финансовые операции ради теста.
5. **Instagram.** Настоящий приём/отправка не проверены. Legacy-код оставлен; WhatsApp не переводить обратно на Meta.
6. **Надёжность отправки при аварии.** Нет durable outbox/exactly-once: crash между фиксацией approval/reservation и транспортом оставляет неоднозначную попытку. Частично отправленные multipart ответы требуют reconciliation по provider IDs, а не слепого повтора. Не закрыты полные Telegram update/session TTL dedup и гонки редактирования активного черновика.
7. **Нагрузка.** Дополнительное PG-соединение для lock не проверено под нагрузкой; при принудительном разрыве lock connection нет отдельного fencing. Оценить лимиты соединений до масштабирования.
8. **Переносимость инфраструктуры.** В snapshot отсутствуют production схема/миграции Supabase и deployment manifests. Не обещать автономный запуск CRM одним docker compose. Production frontend история расходится с origin; backend содержит чужие незакоммиченные изменения.
9. **Диск сервера.** При передаче свободно около 1.9 ГБ из 48 ГБ (96% занято). Три собственных rollback Next build сохранены проверенными `.tgz`; исходные копии заменены архивами. Нужен отдельный план ёмкости; чужие backup и образы не чистить автоматически.
10. **Будущий полностью автономный консультант.** Не реализован/не активирован. Локальное демо — по правилам. Сначала подтвердить бизнес-инструкции, данные наличия/цен, запись, эскалацию и безопасный rollout; не включать общий autopilot в рамках проверки.
