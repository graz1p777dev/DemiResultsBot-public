# Как работает DemiResults

Описание кода и проверенного устройства системы на 23.10.2026. Публичный snapshot не является полной инфраструктурной копией production. Актуальные ограничения — в PROJECT_HANDOFF_RU.md.

## Путь сообщения

```text
Клиент WhatsApp
  → Green API webhook
  → CRM: клиент, диалог, сделка, сообщение и вложение
  → защищённый backend /admin/crm/incoming
  → сохранение + проверка дубликата
  → Redis / Celery: буфер 30 секунд
  → AI-обработка или ручная обработка
  → карточка согласования в Telegram / CRM
  → сотрудник: подтвердить / изменить / отклонить
  → outbox → CRM channel-send → Green API → клиент
  ← статусы отправки, доставки и прочтения
```

Буфер объединяет серию сообщений: более ранняя задача не должна готовить отдельный ответ, если уже поступило новое сообщение. 30 секунд — действующее production-настроенное значение, а не обещание полного времени ответа. К нему добавляются очередь, AI и доставка карточки. Для лида с выключенным AI сообщения сохраняются, но черновик автоматически не запускается.

### Что делает AI

Определяет характер запроса, готовит ответ с бизнес-инструкциями, памятью и доступными слотами, проверяет ответ, извлекает сведения для CRM. Генерация использует последние 30 сообщений диалога; другие этапы имеют собственную обработку контекста. Покупка, стоп-слова, перехват диалога сотрудником и другие условия имеют отдельные ветки. Это не один универсальный LLM-вызов.

Днём бот предлагает, сотрудник принимает решение. При правке/согласовании сохраняется автор; повторное действие не должно отправлять ответ повторно. Если уже есть незавершённая карточка, дальнейшие входящие остаются для последующей обработки, а не создают бесконечные параллельные ответы.

### День и ночь

По настроенному расписанию 10:00–21:00 Asia/Bishkek требуется согласование. Вне этого времени разрешён один фиксированный шаблон на лид за ночь: магазин закрыт, ответим с 10:00. Ночная AI-консультация не включена. Входящие сохраняются; утренний планировщик проверяет отложенные диалоги каждые пять минут. Это описание политики и кода; полная реальная ночная смена ранее не была доказана наблюдением.

## Компоненты backend

| Компонент | Ответственность |
|---|---|
| Next.js CRM + Supabase | Интерфейс, сотрудники и права, клиенты, сделки, диалоги, Green webhook и транспорт |
| FastAPI backend | Защищённые API, приём сообщений от CRM, согласования и интеграции |
| PostgreSQL бота | Лиды, сообщения, буферы, карточки, outbox, настройки, аудит и AI usage |
| Redis | Брокер задач Celery; не основное хранилище истории клиента |
| Celery worker | Фоновая обработка входящих, AI, отправки и восстановление |
| Celery beat | Запуск периодических задач: восстановление, утро, напоминания, бюджет |
| Telegram | Интерфейс согласования для менеджеров, не WhatsApp-транспорт |

Supabase CRM и PostgreSQL бота — отдельные базы. Они синхронизируются через защищённые API, а не через общий доступ к одной таблице.

## Защита от потерь и повторов

- Идентификаторы входящих помогают отсекать повторный webhook.
- PostgreSQL lock и fence защищают обработку одного лида от конкурирующих задач.
- Условные переходы состояний защищают approve/edit/reject.
- Outbox сохраняет резервирование отправки и checkpoints частей ответа.
- Неизвестный исход отправки требует сверки с провайдером; слепой resend недопустим. API 200 / `queued` не равны доставке.
- Согласования, действия и AI usage сохраняются для аудита.

Это механизмы защиты, не безусловная гарантия exactly-once внешнего провайдера при любых авариях. Старые `send_failed` и исторические буферы нельзя массово пересылать ради проверки.

## AI, квота и соединения

Основной клиент — OpenAI. При подтверждённой ошибке исчерпанного баланса поддерживаемый текст переходит на существующий DeepSeek fallback. Лишние quota retries отключены, повторная проверка OpenAI — через пять минут на процесс или при смене ключа. Временные сетевые ошибки и обычный rate limit сохраняют свои повторы.

AI-клиенты теперь переиспользуются в пределах процесса и потока: последовательные вызовы могут использовать существующий пул соединений. OpenAI и DeepSeek разделены; смена ключа закрывает прежний клиент, а после fork создаётся другой. Закрытие HTTP-ресурсов сверено с [официальной документацией SDK](https://developers.openai.com/api/reference/python#managing-http-resources). Модели, prompts, согласование и буфер этой оптимизацией не менялись.

Голосовые сначала нужно действительно распознать, затем передать текст в AI. Текстовый резерв не распознаёт аудио. Последняя подтверждённая проблема ASR — отказ активного OpenAI-ключа по балансу; новый ключ ещё не проверен/не установлен. Без расшифровки голосовое сохраняется и передаётся человеку, а не выдаётся за понятый текст.

## Что оптимизировать следующим

1. Ёмкость диска: при проверке свободно около 1.9 ГБ, занято 96%. CPU и RAM не были узким местом. Нужны расширение или отдельный согласованный retention-план, без удаления чужих backup/rollback.
2. Измерить отдельные стадии CRM ingest до изменения SQL/RPC: несколько последовательных запросов могут добавлять задержку, но их объединение должно сохранять восстановление после частичного webhook.
3. При росте нагрузки вынести ожидание между частями ответа из worker в отложенные задачи. Сначала проверить порядок частей, outbox и аварийное восстановление; простое удаление пауз меняет поведение.
4. Восстановить ASR и завершить реальные Telegram-click, ночной и полный CRM/roles сценарии. Unit tests и health не заменяют эти проверки.
