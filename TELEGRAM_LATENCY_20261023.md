# Telegram: сокращение задержки при исчерпанной квоте

23 октября 2026. Буфер оставлен **30 секунд**, как подтвердил владелец. Никакого replay старых заявок или отправки тестовых ответов клиентам не выполнялось.

## Изменено и установлено на production

- SDK OpenAI 3.10.0 больше не повторяет HTTP 429 с кодом `credit_balance_exhausted` или `insufficient_quota`. Обычный rate limit и временные ошибки сохраняют прежние повторы.
- Внешние Tenacity-повторы также исключают эти две ошибки квоты.
- После подтверждённого отказа поддерживаемые текстовые запросы сразу используют существующий DeepSeek fallback в течение пяти минут в каждом процессе. Затем OpenAI проверяется снова. Изменение ключа сбрасывает обход; ключ не сохраняется вне памяти процесса.
- Ограничения fallback сохранены: не распространяется на аудио, изображения, tools, JSON schema или явный opt-out. Это не исправление ASR и не пополнение баланса OpenAI.
- Заменён только `services/openai_service.py` в backend/worker/beat. Проверены hashes, неизменность окружения, pipeline/admin и возможность scoped rollback. CRM, базы, очередь Green и рабочие часы не изменялись.

## Реальные проверки

Синтетические пять последовательных коротких текстовых запросов из production-контейнера, без клиентских данных и записи заявок:

| Замер | До | После |
|---|---:|---:|
| Все пять запросов | 20.182 с | 8.082 с |
| Первый запрос | 5.321 с | 2.858 с |
| Последующие четыре | 3.463–3.926 с | 1.193–1.394 с |

Это примерно 60% сокращения времени **данного синтетического AI-замера**, не обещание такого же ускорения полного клиентского диалога. До исправления каждый запрос получал отказ OpenAI; после — только первый в серии.

Одно техническое уведомление без кнопок отправки клиенту: Telegram `ok=true`, 0.602 с. Backend `/health` healthy; worker/beat запущены; Redis доступен, очередь Celery без накопления. CRM login HTTP 200, чтение сотрудников/сообщений/сделок и Auth health успешны. Green API authorized/online, webhook соответствует настройкам, очередь отправки и очередь webhook пусты.

До обновления обычные карточки занимали примерно 55–64 с от сохранения входящего до черновика, ещё 0.1–4.1 с до Telegram. На момент последней проверки **новой обычной карточки после установки не появилось**: полный реальный путь с новым кодом не измерен. Не запускать для этого старую заявку; наблюдать новое разрешённое входящее сообщение.

Локально: **203 passed + 16 subtests passed**. Новые тесты проверяют реальный SDK с MockTransport, сохранение transient retries, cooldown/expiry/key change, запрет расширения fallback на media/opt-out и отсутствие внешних quota retries. Production env в pytest не использовался.
