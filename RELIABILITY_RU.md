# Согласования и восстановление отправок

Продолжение от 22.10.2026. Функции согласования, расписание и Green API сохранены;
автономный консультант не активирован. Изменения используют существующие таблицы
`messages`, `settings`, `approval_requests`, без production `create_all` и миграции.

## Что изменилось

- Согласование сотрудника, его audit actor и неизменяемый снимок ответа записываются
  одной транзакцией. Падение до транспорта оставляет `pending_dispatch`, а не теряет
  согласованный ответ. Beat запускает `resume_outgoing` каждую минуту.
- Условный переход разрешает только одному исполнителю начать транспорт. После
  начала отправки неизвестный результат **не повторяется автоматически**.
- Multipart сохраняет каждый известный Green ID. Частичный ответ не считается
  завершённым. Delivery callback не затирается устаревшим объектом отправителя.
- После успешного транспорта, но до завершения карточки/обучения, восстановление
  завершает согласование без новой отправки. Конкурирующая запись training example
  сериализуется блокировкой существующей строки согласования.
- Telegram `update_id` сохраняется до обработки. Повтор подтверждается без запуска
  обработчика; другое содержимое с тем же ID даёт 409. Секрет и actor проверяются
  до резервирования ID. Незавершённые updates остаются для диагностики.
- Сессии правки/перевода/заметки/отказа живут 30 минут, потребляются атомарно.
  Новое действие заменяет предыдущий режим ввода. Медленная AI-правка и перевод
  не перезаписывают более новую правку сотрудника или закрытую карточку.
- PostgreSQL fence дополняет session advisory lock: каждая ORM-транзакция проверяет
  и блокирует epoch лида. После смены владельца старый worker прекращает записи.
- Готовый ночной шаблон отменяется после окончания своей ночи. Утром остаётся
  обычная обработка входящих с согласованием; вчерашнее «магазин закрыт» не уходит.

## Состояния

| Outbox state | Действие |
|---|---|
| `ready` / `pending_dispatch` | Провайдер ещё не вызван; безопасное автоматическое восстановление |
| `sending` | Исполнитель начал попытку; после аварии требуется сверка |
| `uncertain` | Timeout/ошибка после начала транспорта; автоматический повтор заблокирован |
| `completed` | Все части приняты транспортом; это не подтверждение чтения |
| `cancelled` | Ночное окно истекло до начала отправки |

Старые записи без outbox не преобразуются в новые отправки. При rollback на старый
код новые ready-записи сохраняются, но их восстановление потребует возврата новой
версии. Нельзя удалять такие messages ради повторного approve.

## Диагностика и сверка

`GET /admin/delivery-recovery` защищён действующим `X-Admin-API-Key`. Возвращает
ограниченный список номеров строк, состояний, количества принятых частей и stuck
Telegram updates. Тексты клиентов, телефоны, токены и тела provider errors не выдаются.

Для `sending`/`uncertain` сначала сверить известные provider IDs, статусы CRM/backend
и журнал Green. Для неизвестной части проверить историю самого провайдера. Если
провайдер принял сообщение, восстановить учёт по подтверждённому ID; не посылать
текст заново. Если исход нельзя установить, оставить попытку заблокированной и
передать сотруднику. Диагностический endpoint read-only, команды слепого resend нет.

У Green transport здесь нет подтверждённого provider-side idempotency contract.
Поэтому exactly-once при разрыве между принятием провайдером и фиксацией его ID
не обещается. Сохранность намерения, однократный конкурентный старт и запрет
неоднозначного повтора проверены; неизвестная доставка требует reconciliation.

ограниченный live-тест на актуальном согласованном контакте. Текстовый fallback
не устраняет исчерпанный баланс транскрипции/vision.

## Production после обновления

Код `76feb41` узко внедрён в backend/worker/beat. Источник и runtime сверены,
scoped backup прочитан, rollback-образы подготовлены до переключения. Health и
DB health OK; защищённая диагностика HTTP 200, анонимные запросы/неправильный
Telegram secret дают 401; действующий worker регистрирует восстановительную задачу.
Приватные пути/артефакты отката хранятся на сервере, в публичный git не добавлены.

Живые проверки на синтетических WAV и PNG подтвердили внешний блокер: OpenAI
возвращает `429` с признаком исчерпанной квоты и для транскрипции, и для vision.
Instagram identity проверен read-only: HTTP 200 и совпадение настроенного ID.
Реальная доставка Instagram и голосовых клиенту всё ещё требует контрольного контакта.

16 исторических `send_failed` не имеют provider ID. Они сохранены без автоматического
повтора и видны оператору через диагностику. Новый outbox не превращает неопределённую
старую доставку в достоверную: эти записи требуют отдельной reconciliation.

Настоящие Telegram-клики требуют человека в Telegram и согласованного тестового
диалога. Разовая read-only проверка прошедшей ночи назначена на 23.10 после открытия
(Asia/Bishkek); при отсутствии реальных входящих результат будет неполным.

Временные QA-контейнеры, образы, исходники и ровно 20 идентифицированных cache
records этого продолжения удалены. Остались рабочие сервисы и проверенные rollback
артефакты. Свободно около 2 ГБ из 48 ГБ (96% занято); общий вопрос ёмкости этим
не закрыт. См. CAPACITY_RU.md. Чужие backup, образы и базы не очищались.
